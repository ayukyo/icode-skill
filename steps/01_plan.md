## 前置：limit 硬基线（柔性提示）

**目的**：把 [`/icode limit`](../steps/limit.md) 维护的项目约束红线作为 plan 步骤的硬基线，确保 plan §3 架构设计 / §4 ADR / §6 异常处理与 limit 条目呼应（避免"计划正确但违反工程红线"的返工）。

**柔性提示**（**不阻断 plan 流程**）：

1. **路径解析**（同 `/icode limit` 步骤）：先解析 `PROJECT_ID` = `basename(git rev-parse --show-toplevel)`
2. **主存 + 覆盖检测**：
   - 检查全局主存 `~/.claude/icode_data/limits/<project_id>.md`（如不存在则跳过）
   - 检查覆盖 `<project_root>/.icode_output/limit.local/<project_id>.md`（如不存在则跳过）
3. **存在性分支**：
   - **都不存在** → 输出 `💡 本工程尚无 limit 约束（建议运行 /icode limit <约束描述> 生成），不阻断 plan 流程` —— **不报错、不强制**
   - **存在** → Read 主存 + 覆盖（**local 完全覆盖 main**，同 limit 步骤合并逻辑），结果进 plan 步骤的强制思考前置块作硬基线
4. **应用契约**：plan §3 架构设计 / §4 ADR / §6 异常处理须呼应相关 limit 条目（"本工程 limit 红线 N：X，本方案选择 Y 因为..."）；**计划文本一旦引用 limit 条目（出现「红线 N」/「红 N」）必须写入 metadata `limit_refs` 数组**（每条含 `redline_no` + `source` + `title` + `applied_in` 引用章节）；计划**完全未引用** limit 时才允许留空（见下方「强制操作」的「limit_refs 机器自检」）

**与历史检索复用的关系**：limit 硬基线是**项目级约定**（长期稳定），历史检索是**跨工单经验**（临时参考）——两者**互补不替代**。limit 不存在不影响历史检索的注入决策。

## 前置：schema 迁移（自动/幂等/原子）

> 自动识别 + 自动迁移：用户无需任何操作，进入步骤 1 时若检测到 `.ico_metadata.json.template_version` 缺失或旧于当前版本，**自动**在已存在的 `01_plan.md` 末尾追加 §1.5 工程结构快照、补写 metadata、原子落盘；幂等（已含 §1.5 则跳过），失败兜底静默（不阻塞主流程）。

**自动执行**（强制，写在「执行步骤」第 1 步前）：

1. Read `.ico_metadata.json` —— 读 `template_version` 字段（缺失视为 `"v0"`）
2. 与当前 `PLAN_TEMPLATE_VERSION = "v1.1"` 比对（含 §1.5 工程结构快照、模板演进机制），若 `template_version` 已经 ≥ `"v1.1"` → 跳过本次迁移
3. 否则执行迁移 **（原子，不破坏既有正文）**：
   a. 解析既有 `01_plan.md`，用 **`grep -F '工程结构快照（v1.1 自动迁移）'`** 检测是否已含（**必须用 `-F` 字面量模式，不能用 regex**，否则 marker 内的 `(` 与年份误判）；不存在则执行迁移
   b. 自动生成 §1.5 工程结构快照——来源两条（按以下优先顺序）：
      - **优先**：若 `~/.claude/icode_data/project_docs/<project_id>/<branch_safe>/` 有章节，从 `00_overview.md` 的「核心模块清单」+「全栈图」段截取关键列表（≤80 行）
      - **次选**：无知识库时，临时 grep（`ls -la` 顶层目录 + `grep -rn 'int main\|class \w` 找 entry 函数），输出 ≤30 行快照
      - **零退化**：两条都无（纯新工程、无任何源码）→ 输出 `[无工程结构快照-工程无可索引内容]`，不阻塞
   c. §1.5 段追加到 `01_plan.md` 末尾（在所有现有章节之后），原子写：先写 `.tmp` 再 `mv`
   d. 写回 metadata：增字段 `template_version = "v1.1"`、增 `migration_log` 数组追加 `{from, to, at, files=[01_plan.md]}` 条目、`at = date +%Y-%m-%dT%H:%M:%S` 取系统时间（不写死）
   e. 输出 `▶ 自动迁移 → v1.1：补全 §1.5 工程结构快照（迁移到 .ico_metadata.migration_log）`
4. 任一步失败（文件 I/O 错、grep 不可用、project_docs 不可达）→ 静默跳过迁移、记 `[迁移跳过-原因]` 到 metadata migration_log，主流程继续

**与步骤 4/5 迁移的关系**：三步各自独立、各自检测、各自写入 ——
- 步骤 1 迁移在 `01_plan.md` 写 §1.5 工程结构快照
- 步骤 4 迁移在 `03_plan_final.md` 写三链预扫段
- 步骤 5 迁移在 `05_deepcheck.md` 写 blast-radius 三链自检段
- 三段互补不重复写入同一文件、互不依赖；migration_log 数组会按顺序记录全部迁移

**向后兼容**：

- 旧工单（缺 `template_version`）一律视为 `v0`，自动升级到 v1.1
- 已迁移的 01_plan.md 再次进入步骤 1 不会重复追加（按 `grep -F '工程结构快照（v1.1 自动迁移）'` 字面量检测去重）
- 用户手改过的 `01_plan.md` 原文**不会被覆盖**——只在末尾追加新段
- metadata 字段新增（`template_version` / `migration_log`）一律非破坏性，旧 metadata 缺这字段视为默认（`v0` / `[]`），写回时整对象保留

### 接口误用预审（plan 阶段反推核心机制，治「下游易误用」盲区）

- **目的**：现有设计都是「我设计时考虑下游」，**没有「上游调用者能否正确使用我设计的接口」的反向推演**——参数顺序是否易混？返回类型是否易误用？错误码是否语义明确？这些到 04_code 集成阶段或运行时才暴露，返工成本高。**本节强制从调用者视角反向审视每个新增 public 接口，预审 ≥3 个可能误用方式并逐一给出设计态缓解**
- **与「接口克制」的关系**：接口克制管「不暴露不必要的」，接口误用预审管「暴露出去的不要易误用」——前者治过度设计，后者治误用设计，两者互补
- **范围**：覆盖本计划**所有新增 public 符号**（类 / 函数 / 枚举 / 宏 / 全局变量）。每个新增 public 符号一张子表
- **格式**（每个 public 符号一张子表，≥3 个误用视角）：

  | 误用视角 | 可能的误用场景 | 实际会发什么 | 设计态缓解 |
  |----------|----------------|--------------|------------|
  | 参数顺序混淆 | 调用 `Foo(a, b)` 写成 `Foo(b, a)` | 类型相同则编译通过，运行时语义错 | 强制参数类型不同 / 用 builder 模式 / 关键参数前置 |
  | 返回值误判 | 返回 `int` 但实际语义是 enum | 调用者按 `!= 0` 判断状态，漏掉负数错误码 | 改用 enum class / 文档明确所有可能返回值 |
  | 错误码吞没 | 调用者忽略非 0 返回 | 错误状态继续传播 | 改用 Result 模板类型（Result&lt;T, E&gt;）/ 关键接口加 WARN 日志 / 文档警示 |
  | 资源所有权不清 | 谁负责释放 `Foo*` 返回值 | 调用者漏释放或双重释放 | 文档明确所有权 / 用 unique_ptr / 加 RAII 包装 |
  | 异步回调时序 | 回调在持有锁时被触发 | 死锁 | 文档明确回调上下文约束 / 在接口签名注明「must not hold lock」 |
  | 枚举值越界 | 调用者传未定义 enum 值 | switch 漏 case，行为未定义 | enum class + 默认分支抛异常 / 文档列出所有有效值 |

- **必填列**：误用视角 / 可能的误用场景（具体到调用代码）/ 实际会发什么（运行时后果）/ 设计态缓解（接口签名、文档、类型、默认值哪一层防）
- **反推自检**（写在表后）：
  - 每个新增 public 符号**至少 3 个误用视角**（不能凑数；少于 3 个 = 该符号设计足够简单，需在自检段说明为何不需要 3 个）
  - 每个误用必须有**具体缓解措施**（不能写「文档警示」了事——文档警示是兜底，不是缓解）
  - 与「端到端路径推演表」交叉验证——推演表里的每个调用点在本节有对应误用预审
- **新增 public 符号为 0 时**：本节写「无新增 public 符号（仅修改既有 internal 实现），误用预审不适用」，不强行凑 3 个
4. **架构决策记录（ADR）** — 每个关键决策记录：上下文、候选选项、决策、理由。格式如下：

   ```markdown
   ### ADR-N: {决策标题}
   - **上下文**：为什么需要做此决策
   - **工程既有模式调研**（决策前必做，grep 实证）：当决策涉及"如何调用既有方法/接口/跨模块协同"时，必须先 grep 工程里同类调用的既有写法，把统计结果写在此处。统计字段：直调 N 处 / 间接调用（路由/事件/注册分发）M 处 / 其他 K 处；结论：工程既有主导模式是 X（若多种并存，说明各自适用场景）。**不得凭"内部触发更简单"等直觉选调用方式，必须以工程既有模式为准**。
   - **现有功能覆盖度检查**（涉及新增功能/新增接口/新增模块的 ADR 必做）：按 [references/necessity_check.md](../references/necessity_check.md) 全工程检索确认无等价实现，结论写 `未覆盖` / `部分（边界）` / `已覆盖（file:line）`。纯内部重构（无新增功能语义）标「本 ADR 无新增功能语义，覆盖度检查不适用」。
   - **选项**：A) xxx  B) xxx  C) xxx  **X) 不做（现有实现已覆盖：file:line）**——涉及新增功能/接口/模块的 ADR，候选选项**必须**包含 X；若覆盖度检查判「已覆盖」，直接决策「不做」并说明理由，不进入设计
   - **决策**：选择 X
   - **理由**：为什么选 X 而非其他（须呼应「工程既有模式调研」结论——若选与主导模式不同的方案，必须给出强证据）
   ```

   > **根因优先选型准则（多方案并存时的强制排序）**：ADR 枚举方案时，**第一优先 = 修正缺陷逻辑本身（root cause）**——候选同时含「修错逻辑」与「规避 / 重试 / 打补丁 / 加配置开关」两类时，**默认选修正逻辑**，规避类自动降级。选规避必须先给出**可验证**的「根因为何不可行」论证（不可行理由必须是事实，不能是推测）。每个含规避类候选的 ADR 必须自答强制判定问题：
   > 「这个修复是在**修正错误的逻辑**，还是在**绕过错误逻辑**？如果是绕过——根因真的修不了吗？绕过是否只覆盖了单点？」

   > **安全红线 ≠ 放弃根因修复的理由**：「保持安全门控」与「修正错误逻辑」**不是互斥**——根因方案必须**同时满足红线约束**，而不是因红线直接排除根因选项（红线联动见本步骤「limit 硬基线」段）。引用红线时补一句强制说明：
   > 「红线 N：X；根因方案 Y 以 Z 方式保持该属性（不削弱），故选 Y 而非规避」。

   需记录 ADR 的典型场景：方案选型、降级策略、接口取舍、兼容性权衡、**跨模块/跨端点调用方式选择**（直调 vs 路由/事件分发）、**跨层翻译入口点选择（在哪个边界做归一化：数据入口适配器 vs N 处散补丁）**。决策变更时只需更新此章节 + 受影响的引用点。

   > **与 `00_init.md` 第5节待决策项的关系**：若 `00_init.md` 第5节列了某待决策项的初步倾向（步骤0「待决策倾向自审」产出），步骤1 ADR **必须独立评估**该决策，不得直接照搬 init 倾向作为 ADR 决策；若 ADR 决策与 init 倾向一致，「理由」字段须附独立 Read/Grep 调研证据（呼应上方「工程既有模式调研」），不得仅引用"init 已倾向 X"作为 ADR 理由。（注：init 第5节标"无代码证据-留步骤1 ADR"的纯设计/产品偏好项除外，其 ADR 理由记设计依据即可，不要求 grep 证据）

   > **历史溯源（可选）**：若本 ADR 的决策实质借鉴了历史检索命中的相似工单，在「理由」末尾追加一句 `(参考相似工单 {ticket_id} 的同类决策)`。这是决策溯源而非工程污染，仅限实质借鉴时使用，不得堆砌。
5. **模块详细设计** — 每个模块的职责、关键函数、数据结构，引用现有接口命名风格。**代码示例使用伪代码+关键行号引用**，禁止粘贴完整函数实现（完整实现留给步骤4编码阶段）。格式：`参考 src/foo.cpp:42-68 的 HandleXxx 模式`。**必须说明新增代码如何融入既有链路习惯**（命名模式/错误处理模式/调用链模式/日志模式），不得写出"功能对但风格突兀"的设计

### 端到端路径推演表（plan 阶段反推核心机制，治「链路完整性漏洞」盲区）

- **目的**：现有验证都是「静态核对」（断言存在吗？模式对吗？），**没有「按方案走一遍 happy path + 异常 path」的端到端推演**——链路完整性漏洞要等 04_code 实跑才发现。**本节在设计阶段就把核心数据流在脑子里走一遍，逐环节核对预期行为与异常分支**，治「链路看着对但跑起来断」型漏洞
- **与 §6 链路图的关系**：§6 链路图是「一图流总览」（节点 + 箭头 + file:line 锚点），本表是「链路图的逐环节细化」（每个节点的预期输入/行为/异常分支/可达性）。两者互补，图给总览、表给细节
- **范围**：覆盖**所有核心数据流**（用户/外部输入 → 模块入口 → 中间处理 → 模块出口 → 持久化/外部输出）。每条数据流一张子表
- **格式**（每条数据流一张子表）：

  | 步骤 (file:line / 模块) | 预期输入 | 预期行为 | 异常分支 | 是否可达 |
  |------------------------|----------|----------|----------|----------|
  | 入口 A.foo (src/a.cpp:42) | 调用方传的 X | 返回 X 的归一化结果 | X 为空 → 返回默认值 | [已推演] 或 [未推演-原因] |
  | 模块 B.bar (src/b.cpp:88) | A 的输出 | 处理后转 C | 处理失败 → 走降级路径 D | [已推演] 或 [未推演-原因] |
  | 出口 C.baz (src/c.cpp:15) | B 的输出 | 写持久化 | 写失败 → 上报 + 回滚 | [已推演] 或 [未推演-原因] |

- **必填列**：步骤（含 file:line 锚点，否则不算落实）/ 预期输入 / 预期行为 / 异常分支（不是空就填「无/正常路径唯一」）/ 是否可达（`[已推演]` 或 `[未推演-原因]`）
- **必须覆盖的异常分支**：边界值（0/极值/空）、状态机非法转换、外部依赖不可用、并发竞态、时序错位、错误返回路径
- **反推自检**（写在表后）：
  - 每条数据流**至少 1 个异常分支**被推演（不能整列「无」）
  - 所有 `[未推演]` 必须有具体原因（不能说「待补」了事）
  - 与 §3 接口定义的「每个 public 符号的必要性」呼应——表中每个调用点对应一个必要 public 符号
- **不写代码，只推演路径**：禁止把本表当代码实现写，详细实现留给步骤4编码阶段

### 状态机链路推演（涉及状态机/多态流程修改时必填）

> **触发条件**：修改涉及一条**穿过多层状态机 / 跨模块状态流转 / 严格前置守卫**的数据流（如续接、嵌套、跨模块守卫链）。普通单层数据流不触发，避免加重常态负担。

- **目的**：端到端路径推演表是**数据流视角**（步骤/预期输入/预期行为/异常分支/可达性），对穿过多层状态机的路径**无法逐层标注状态与守卫**。本子段把每个子步骤的**各状态机当前状态 + 关键守卫 flag + 前置守卫是否满足**逐层摊开，抓「父子嵌套调用内部的分支被漏推演」型漏洞（子函数内部按 flag 走不同分支时，仅看外层调用表覆盖不到）。
- **格式**（每条状态机链路一张子表）：

  | 步骤 | 状态机A状态 | 状态机B状态 | 关键守卫flag | 引擎/外部系统状态 | 前置守卫是否满足 |
  |------|-----------|-----------|-------------|-----------------|----------------|
  | <子步骤 (file:line)> | <状态> | <状态> | <flag=T/F> | <running/...> | ✅/⚠️ <原因> |

- **必填列**：步骤（含 file:line 锚点）/ 各状态机当前状态 / 关键守卫 flag / 引擎或外部系统状态 / 前置守卫是否满足（`✅` 或 `⚠️ + 原因`）。
- **特别检查**：每个子步骤的**子函数内部分支**（如某 prepare 类函数内部按 flag 走不同分支）是否已被标记 `⚠️` 并推演——这是本子段相对端到端推演表的核心增量。
- **反推自检**：状态机链上**任一步前置守卫不满足或状态转换非法**，必须标 `⚠️` 并给出处理分支，不能整列 `✅`。

   b.5 **§10 需求质量清单（本次新增 inline·必填）**：

   **目的**：plan 写完后立即自检需求本身质量——**"为自然语言写单元测试"**（本次新增 inline）。覆盖**需求本身**的 10 个质量角度，不是实施步骤检查点（§8）。每条 AI 勾对 ✅/⚠️/❌ + 简述。

   **与 §8 校验项区分**：
   - §8 校验项 = 实施步骤检查点（步骤 4/5/6 验证用，每步打勾）
   - §10 checklist = 需求本身质量自检（plan 完成后立即做，覆盖需求覆盖度/边界/异常等质量维度）

   **10 个检查角度**（AI 自动生成具体内容 + 勾对）：

   | # | 检查项 | 关注点 |
   |---|---|---|
   | 1 | **需求覆盖度** | 计划是否覆盖了 init/log/命令行参数中所有需求点？grep 需求关键词对照 §2 功能需求 |
   | 2 | **边界覆盖** | 是否明确列出了边界值（0/负数/空/极值/INT_MIN 等）？参考工程数值边界自检 |
   | 3 | **异常路径** | 是否覆盖了所有错误码/异常分支？是否对照工程错误码定义（CALC_ERR_*）？ |
   | 4 | **数据契约** | 新增/修改接口的参数/返回值类型是否明确？是否有 NULL/越界防御？ |
   | 5 | **接口约束** | 新增 public 符号是否有必要性论证 + 接口误用预审（≥3 个误用视角，§3.1）？ |
   | 6 | **limit 一致性** | 计划是否与本工程 limit 红线一致？（如有 limit）—— Read main + local，对照 §3/§4/§6 是否违反 |
   | 7 | **可测试性** | 是否有可执行的测试计划（含正常路径 + 边界用例 + 异常用例）？ |
   | 8 | **可回滚性** | 是否有明确的回滚方案（git revert 命令 / feature flag / 灰度策略）？ |
   | 9 | **依赖清晰** | 是否列出了所有外部依赖（含版本/库名/链接方式）？新增依赖是否在工程既有依赖基础上？ |
   | 10 | **文档化** | 是否在代码注释中说明了关键决策（why not just what）？§5 模块详细设计是否引用既有模式？ |

   **勾对格式**（每条独立）：
   - ✅ [通过]（勾选项 + 简述证据）
   - ⚠️ [部分通过]（具体不足 + 影响范围）
   - ❌ [未通过]（具体问题 + 必须改进）

   **失败处理**（**不强制阻断流程**，但**可见性提示**）：
   - ❌ 项 > 3 条 → metadata 写入 `checklist_status="fail"`，audit 入口输出警告（"本工单 §10 checklist 多项未通过，审计会重点检查"）
   - ⚠️ 项 > 5 条 → metadata 写入 `checklist_status="partial"`
   - 全部 ✅ → metadata 写入 `checklist_status="pass"`
   - **不阻断 plan 流程**（不强制回 init 修订）—— 跟现有 icode 风格一致（柔性提示）

   **与 limit 协同**（关键价值）：

   - 与 plan §3/§4/§6 引用契约**双向验证**：§3/§4/§6 已显式引用红线，§10 #6 再核对"是否真的遵循"
   - 形成"plan 引用红线"+"checklist 核对红线"双保险

   **与 §4.5 4 维度设计态的关系**：
   - §4.5 = 同事提示词"修 bug 后做代码 review 修复" 4 维度（根因/逻辑/竞态/日志）
   - §10 = 需求质量 10 角度清单（plan 完成后立即自检，"为自然语言写单元测试"）

   c. **断言验证**（必须执行，不可跳过）：
      从计划中提取所有涉及具体代码位置/行为的断言，逐一用 Read/Grep 工具实证验证。断言分五类：
      - **接口存在类**（原有）：如"某函数在文件X中且 public"、"某实例可通过 GetXxx() 取得"
      - **路径可达类**（原有）：如"某配置从Y加载"、"某接口签名是Z"
      - **调用模式一致性类**（原有）：对计划中每个"跨模块/跨端点/跨层"调用，grep 同文件/同模块既有同类调用的写法，核对新增调用是否对齐工程主导模式。若工程有明确主导模式（如同类调用 N 处都走路由、0 处直调），新增调用必须对齐，否则断言失败 `[未验证-调用模式不一致]`，计划必须修正。**同函数内既有同类调用是最强信号**——同函数已有调用走某模式，新增调用不得另选他法。
      - **覆盖类**：对计划每个"新增功能点/新增 public 接口"，断言"工程现有代码无等价实现"——按 [references/necessity_check.md](../references/necessity_check.md) 全工程检索 + Read 命中处行为链（证据 file:line）。验证失败（发现等价实现）→ 标 `[未验证-发现现有等价实现]`，**计划修正（需求点改复用/删除），不是修断言**
      - **首次激活路径一致性类**：当修改涉及一条**从未被实机执行过**的历史代码路径时，核对**跨层接口双侧校验一致性**。定义与完整核对清单见 [references/first_activation_path.md](../references/first_activation_path.md)。对 plan 涉及的每个跨层接口 / 请求 action：grep 历史日志确认是否有**成功调用记录**；若无（首次激活路径）→ 断言"请求方入参校验 与 接收方校验 对同一字段的接受值要求一致"，Read 两侧逐字段对比 → 不一致标 `[未验证-双侧校验矛盾]`，**计划必须同时修两侧**。**软信号**：历史日志可能不全，命中只触发核对，不阻断；严禁当硬性失败

      - 已验证的断言标记为 `[已验证]`
      - 验证失败或未验证的断言标记为 `[未验证]`，并说明原因
      - 验证失败导致计划需要调整的，立即修正对应章节
      - 将验证结果追加到计划末尾的"断言验证记录"章节

   c.5 **方案对抗验证**（plan 阶段反推核心机制，治「自验自证」盲区）：
      - **目的**：断言验证是「我设计时核对证据」，**对抗验证是「第三方攻击方案可行性」**——独立质疑者从可行性/兼容性/调用链完整性三视角攻击方案，撑不住就降级/修正，不让漏洞流到 04_code 才暴露。**复用 log 阶段对抗模式**（独立质疑者 / 诚实降级 / 证据回指），但 plan 阶段不需 log 那么重——max **2 轮**收敛（log 默认 4 轮，plan 方案范围更聚焦，2 轮足够）
      - **三视角质疑者**（任一独立 spawn，禁用 Explore，用 general-purpose + schema 强制结构化）：
        - **可行性质疑者**：方案是否真能在现有架构下实现？是否有未识别的依赖/前置条件？修改范围是否被低估？
        - **兼容性质疑者**：方案是否破坏既有功能？是否引入回归？上下游依赖是否被忽略？API 变更是否兼容？**方案必要性**：方案是否在解决一个已被现有代码解决的问题？输入文件中是否有与方案功能重叠的现有实现？——若发现重叠，必须质疑方案必要性并回指 file:line
        - **调用链完整性质疑者**：方案涉及的所有跨模块/跨端点调用，调用链是否完整？返回路径是否闭环？异常分支是否都有出口？
      - **输入契约**：质疑者输入 = 方案涉及的文件 + **`rg -in '<需求关键词>'` 命中的非计划文件**（全工程检索，含计划未涉及模块）。质疑者看不到重叠文件就永远不会质疑必要性——grep 命中文件必须喂给质疑者
      - **收敛与降级**：
        - 有实质反驳 → 修正方案 / 补证据 / 降级标 `[未验证-对抗不通过]`
        - 2 轮后仍有质疑 → 标 `[部分通过]`，剩余质疑点写入「方案对抗验证记录」末尾「残余风险」段
        - 环境无 spawn 工具（`no_spawn_env = true`）→ 主代理代行三视角独立判断，但不得自演一致假共识；产物文件强制明示「主代理代行（环境无 spawn 工具）」
        - 子代理超时/失败 → 按 [references/adversarial.md](../references/adversarial.md)「子代理失败处理」重试 2 次（含 1 次换 subagent_type） → 仍失败标 `[未验证-子代理对抗失败]`，**禁止主代理补齐为代理代行**
      - **产物**：将对抗记录追加到 `01_plan.md` 末尾「方案对抗验证记录」章节（与「断言验证记录」并列），每条记录注质疑者 spawn Agent ID 或「主代理代行」标注
      - **与现有「c. 断言验证」的关系**：断言验证是「静态核对」（接口存在吗？模式对吗？），对抗验证是「动态攻击」（方案撑得住第三方攻击吗？）——两者互补，前者治「细节错」，后者治「方向错」，缺一不可
