# 现有功能覆盖度检查（共享规则）

> 本文件是 icode「现有功能覆盖度检查」的共享规则（触发时机 + 执行命令 + 命中处理 + 三类判定 + 落点）。各步骤只声明"检查对象"（需求点/功能点/新增接口），执行流程引用本文件。涉及步骤：init §2/§5、plan §3 前置/断言/ADR/对抗、review 维度 7/对抗输入、deepcheck Reverse 对比、audit §6.7 视角 C。

## 为什么必须做

icode 全流程的默认视角是「计划 → 实现 → 验证」——检查"计划要做的做对了没"，但**不检查"计划要做的事是否已经被现有代码实现"**。本机制补上反向校验：**每个新增需求点，先确认现有代码没有等价实现，再进入设计**。

实战教训：某工单计划"新增某参数生效拦截"（per-item 门控），走完全流程（编译通过、复检 0 issue、终审全通过）后，才发现另一已有模块在入口处已做**全局拦截**——新增拦截永远不会执行（入口先返回），且语义与现有实现冲突。全部回退、零修改交付。根因：调研时 grep 到过该模块的同类参数消费点，只当"消费点"记录，**没有读上下文、没有追它消费后做了什么**——看到"已有消费"就跳过，而不是"已有消费 → 它消费后是否已覆盖我的需求"。

**两条铁律**：
1. **grep 命中 ≠ 理解行为**——命中处必须 Read 上下文（整个函数/段落），追它的上下游行为，再判定是否构成完整实现
2. **"现有实现路径存在" ≠ "现有实现已覆盖需求"**——预筛的"路径存在"回答不了"是否重复造轮子"

## 触发时机

| 步骤 | 触发点 | 检查对象 |
|------|--------|---------|
| init | §2 现状盘点之后（步骤4 读码时） | §3 每个新增需求点（A/B/C 全查） |
| plan | §3 架构设计之前（独立于 init 复用） | §2 每个功能点 / 每个新增 public 接口 |
| review | 维度 7「必要性审查」 | 计划每个功能点 |
| deepcheck | Reverse 对比之后 | 逆推出的新增功能/接口 |
| audit | §6.7 视角 C | 最终产物功能点 |

**init 是可选步骤，plan 是必经步骤**——覆盖度检查必须在 plan 独立可执行（无 init 时 plan 自己补做；有 init 时 plan 复核 init 结论，不直接照搬）。

## 执行步骤（AI 直接照填）

### 1. 提炼检索关键词

对每个检查对象，提炼「动词 + 名词」关键词集（2~4 个变体），覆盖同义表述：

```text
需求点："新增某参数拦截"  → 关键词：参数拦截 / 参数生效 / 参数禁止 / 全局拦截
```

### 2. 全工程检索（不限本模块）

**ripgrep 优先**：

```bash
rg -in '<关键词1>|<关键词2>|<关键词3>' '<工程根目录>'
```

- **搜索范围：全工程**，不限需求涉及的模块——已有实现可能在任何模块
- 零命中 → 标「未覆盖（全工程检索无命中）」，检查结束
- 有命中 → 进入第 3 步

### 3. 命中处理三要素（必做，缺一 = 检查不合格）

对**每个**命中处：

1. **Read 命中处上下文**：至少读整个函数/段落（≥20 行），**不得只记录"命中 file:line"就跳过**
2. **若命中处只是消费点/数据通道**（被赋值、被读取、被传输），**追踪其上下游**：谁产生该值 → 谁消费该值 → **消费后做了什么**（判断逻辑/拦截/过滤/窗口判断……），直到追到"行为"而不是"数据"
3. **判定关系**（按下方三类判定规则），每条判定必须带证据（file:line）

> 实战教训内嵌：发现命中处只标"算法无 setter，可在上层做窗口判断"却不读命中处行为链 = 本机制失败。命中处是"可能已实现的现成实现"的调查入口，不是记录点。

### 4. 结论落点

按各步骤落点表（见下）把结论写进产物：
- init：§2 的「2.X 现有功能覆盖度检查」子段 + §5 预筛表「是否已覆盖」列
- plan：§3 前置检查小节 + 断言验证记录 + ADR「不做」选项理由
- review：维度 7 结论（逐功能点）
- deepcheck：Reverse 对比段「现有同类实现对比」表
- audit：§6.7 视角 C 表

## 三类判定规则

| 判定 | 条件 | 处置 |
|------|------|------|
| **已覆盖（重复）** | 现有代码已实现等价功能，且行为语义一致（含"新实现即使写出来也不会被走到/被入口挡掉"的情形） | 需求点改为「复用现有实现」或**删除**；不进入设计 |
| **部分覆盖（补充）** | 现有代码实现了一部分（如只做了数据通道/只做了其中一个环节） | 明确新实现与现有实现的**边界**（谁补哪一段、在哪个环节衔接），需求点改写为"补充"语义 |
| **未覆盖** | 全工程无命中，或命中处行为链与需求无关 | 正常进入设计，标注「覆盖度已查：无等价实现（证据 file:line）」 |

**判定"已覆盖"的强信号**：命中处存在与需求同语义的**拦截/判断/门控**行为（不是只传输数据）；该行为的作用范围**覆盖了需求要影响的全部场景**。

**判定"重复"的兜底验证**（低成本，建议做）：若新实现已写出，把新功能点与命中处行为对比"新实现是否会执行到"——**新实现永远执行不到的 = 重复**（本事件类型）。

## 各步骤落点（消费本机制的产物）

### init §2 子段 + §5 预筛列

- §2 现状盘点后新增「2.X 现有功能覆盖度检查」：逐需求点列出「检索关键词 → 命中位置 → 行为链结论 → 判定」，格式见 [00_init.md](../steps/00_init.md) 模板
- §5 可执行性预筛表新增「是否已覆盖」列（`是（file:line）` / `否` / `部分`）：标「是」的需求点降级或删除，标「部分」的须写明边界

### plan §3 前置

- 复用 init 工单：**复核** init §2 的 2.X 结论（重跑关键词检索确认命中位置仍成立），不直接照搬
- 无 init（直接 `/icode plan`）：独立执行完整检查
- 结论写进 §3 前置小节；每个新增 public 接口也必须过本检查（"已有等价接口"时优先复用而非新增）

### plan 断言验证第四类「覆盖类」

对计划每个"新增功能点"断言：`工程现有代码无等价实现（<检索关键词> 检索：无命中 / 命中已判不覆盖，证据 file:line）`。验证失败（发现等价实现）→ 计划修正（需求点改复用/删除），不是修断言。

### plan ADR「不做」选项

涉及**新增功能/新增接口/新增模块**的 ADR，候选选项**必须**包含 `X) 不做（现有实现已覆盖：file:line）`；若该选项成立（覆盖度检查判「已覆盖」），ADR 直接决策「不做」并说明理由，不进入设计。纯内部重构（无新增功能语义）的 ADR 豁免，明示「本 ADR 无新增功能语义，'不做'选项不适用」即可。

### review 维度 7「必要性审查」

审查每个功能点：grep 现有代码确认无等价实现。发现等价实现 → confirmed issue（`功能点 X 已由 file:line 实现，计划重复`），进对抗验证。**对抗质疑者输入必须包含 grep(需求关键词) 命中的非计划文件**——质疑者看不到重叠文件，就永远不会质疑必要性。

### deepcheck Reverse「现有同类实现对比」

逆推规格 → 对比计划（找差异）之后，**再对比现有同类实现（找重复）**：对逆推出的每个新增功能/接口，按本机制检索全工程等价实现。发现等价 → 按「该修的偏离」处理（计入 has_issues），防"代码与计划一致但计划本身就是重复实现"。

### audit §6.7 视角 C「必要性收敛」

在视角 A（需求 vs 产物）/ 视角 B（limit vs 产物）之外，加视角 C（产物 vs 现有实现）：

| 功能点 | 现有实现（file:line） | 新实现（file:line） | 关系 | 收敛判定 |
|--------|---------------------|--------------------|------|---------|
| 某功能点 | 已有模块入口拦截 | 新增 per-item 门控 | 重复（新实现永不执行） | ❌ 重复实现，走 §6.2 修复 |

## 反推自检（每次执行后勾对）

- [ ] 每个检查对象都有一行结论，**不得静默跳过**（零命中也要写「未覆盖（检索无命中）」）
- [ ] 每个命中处都 Read 了上下文（≥20 行），无"只记 file:line 就跳过"
- [ ] 消费点/数据通道类命中都追到了"行为"（消费后做了什么）
- [ ] 「已覆盖」判定都有行为链证据 + 覆盖范围说明
- [ ] 检索范围是全工程（非仅需求涉及模块）
- [ ] 关键词含同义变体（≥2 个），非单一关键词
