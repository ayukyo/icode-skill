# 强制思考前置——细节规则（按需读）

> 本文件是 icode 强制思考前置的**细节规则**，按需 Read：
> - **各步骤思考子项**：仅在思考时缺参考时 Read（各 step 文件本已声明本步骤子项）
> - **历史参考小节**：仅 init/plan/log/start 检索命中时 Read
>
> 核心规则（每步必读）见 [thinking_core.md](thinking_core.md)。

## 各步骤思考子项（步骤文件已声明本步骤的子项，本节主要作为速查）

- **步骤0 init**（至少5步）：需求分解 → 现状盘点（基于读码） → 影响面分析（基于读码） → 待决策项识别 → 待决策倾向自审（逐条回溯现状/影响面证据，主动找反证；无反证保留、有反证修正并记反证）
- **步骤1 plan**（至少3步）：需求分解 → 方案分析 → 风险评估
- **步骤2 review**（至少3步）：首轮—需求分解→独立方案构思→对比要点预判；续跑—回顾历史轮次问题→增量审查范围界定→跨章节影响预判
- **步骤3 merge**（至少3步）：逐条甄别审查意见 → 判断采纳/驳回 → 规划修改策略
- **步骤4 code**（至少4步）：梳理文件清单 → 规划接口 → 预判冲突点 → 确认注释策略
- **步骤5 deepcheck**（至少3步）：梳理代码清单 → 回顾计划要点 → 制定逆推/Fixed/Free 检查策略
- **步骤6 audit 6.1**（至少3步）：构建追溯矩阵（计划功能点→代码位置）→ 汇步骤历史 → 规划 6 维度审计策略
- **步骤7 readme**（至少4步）：通读产物要点 → 识别报告类型(log/功能) → 提炼自包含内容 → 规划章节结构
- **步骤8 patch**（至少4步）：现状重审要点 → 修改点清单 → 影响面预判 → 复检策略（阶段4 复检子项至少3步：列修改点 → 预判破坏面 → 定复检断言）
- **入口 log**（至少4步）：症状分解 → 基线预判 → 链路假设 → 验证策略

## 历史参考小节（仅 init/plan/log/start 历史检索命中时 Read）

若该步骤启动时历史检索命中（init/plan/log/start），在强制思考文字块里加一节「历史参考」，**按命中工单的 `verdict` 分流标注 + 注入要点**，作为思考输入。详见 SKILL.md「历史检索复用」节（注入形式·按 verdict 分流）。

**按 verdict 分流标注**（字段缺失视为 `unknown`，向后兼容旧工单）：

- `verified`：标 ✅「借鉴参考」，正常注入 ADR/风险/根因/要点
- `unknown`（含所有旧工单，**A 层强制强化，防误导主防线**）：
  1. **扩读 `00_init.md` 末轮对话摘要**（≤0.3K，捞最终结论/证伪信号--工单演进中的方向变更常记在末轮，现状只读 ADR+风险读不到）
  2. 标 ⚠️「结论未经验证标注，ADR 仅为当时决策快照，须甄别是否被后续实机推翻」
  3. **对抗质疑三问**（强制当场判借鉴还是避坑，每问须实质作答不得空泛）：
     - ① 该工单核心方案前提**是否仍成立**？（Read/Grep 实证命中工单工程的当前代码，不盲信历史 ADR）
     - ② 该工单结论**是否被后续实机/审查推翻过**？（查末轮摘要/`06_audit.md` 有无"回退/不可行/推翻/已回退"信号）
     - ③ 该 ADR 是**借鉴**还是**避坑**？（默认怀疑，不默认信任；有推翻信号则转避坑）
- `disproved`（`verdict_review_needed=false`）：标 ⛔「避坑+证伪前提断言」，注 `verdict_reason`（作可验证断言）+`correct_direction`（**不注 ADR**）；**强制验证证伪前提是否仍成立**（对抗质疑第①问的特化--disproved 有明确证伪前提如"某接口语义是重置"，须 Grep/Read 当前实现确认是否仍重置）：仍成立则确实避坑；已失效则方向或可重新考虑，提示 `/icode status --verdict` 标复活
- `disproved`/`superseded`（`verdict_review_needed=true`，证伪前提依赖已变化）：标 ⚠️「曾证伪但依赖已变化，原证伪可能失效」，**不硬避坑**，走 unknown A 层对抗质疑三问 + 注"曾证伪 + 证伪前提 + 依赖变化"提示，让新需求重新评估证伪前提是否仍成立；前提失效则该方向或可重新考虑
- `superseded`：标 🔁「已被替代，参考新方案 {superseded_by}」

**核心原则**：历史参考默认是"待质疑的线索"而非"待照搬的结论"。`unknown` 工单尤其要警惕--它可能是没标过 verdict 的好工单，也可能是没标过 verdict 的坏工单（如核心方案实机证伪但未补标），**靠对抗质疑三问 + 末轮扩读当场甄别**，不靠"有历史参考就采信"。

### 重复模式检查（命中簇重复信号时执行）

**触发（软信号，不阻塞、不下结论）**：段二命中簇 ≥2 条**或**任一条 `hit_count ≥ 3` → 在「历史参考」节加**一行轻提示**：`⚠️ 该模块/症状已出现 N 次，疑似重复模式`。只提示，不判"重复/纰漏"，不触发重动作——命中 2、3 个相似工单**不代表**架构纰漏（同模块高频任务区属正常多次任务），**也不因命中多就自动建议重构**。

**实事求是评估（命中簇 ≥2 时执行；核心 = 每次命中基于当下实证，替代"标记过就不再重来"的机械跳过）**：

1. **查模式状态**：读 `~/.claude/icode_data/patterns.json`，按 `(project_id × module × 症状簇)` 找对应 pattern（`project_id` 取 `resolve_project_id(cwd)`，与工单索引 `project_id` 字段一致——demo 等继承 git 的工程会解析为主仓名，历史工单缺该字段时用 `project_path` basename 兜底；详见 [dir_and_metadata.md](dir_and_metadata.md)「重复模式状态」段）——曾重构工单 `refactor_ticket_id` / 上次 `last_assessment` 是**历史事实参考，非跳过依据**；pattern 有 `workaround` 时提示直接带「上次方案：{workaround}」（从告警升级为可执行知识，无则显示「暂无历史方案」）
2. **核对当前代码实际状态**（Read/Grep 命中工单工程当前代码，不盲信历史结论）：上次重构是否落地？根因是否真解决？有无复发证据？（复用对抗质疑第①问的实证方法）
3. **确定性佐证**（补 LLM 语义盲区，Sentry 指纹式确定性信号）：`project_path` 存在且为 git 仓库时，`git log --oneline --since=90.days -- <模块相对路径>`（`90.days` 是 git approxidate 相对格式，实测跨版本可靠；**`90d`/中文「90天」在此类 git 会静默失效为不过滤，禁用**）统计该路径提交频次，作「该模块反复被改/修」的确定性佐证并入 evidence；路径失效（path_gone）/非 git/匹配不到模块路径 → **跳过**。佐证是**加分项非硬门槛**，缺失不阻塞
4. **三态结论**（实事求是）：
   - **已解决无复发** → 提示「曾重构于 {refactor_ticket_id}，当前实证未复发」→ **不重构**（这是实事求是，不是机械跳过）；并据第 2 步核对结果提炼**已落地的实现/规避方案**（如某防御分支、某算法套路）作为该 pattern 的可执行知识来源
   - **复发 / 未彻底解决** → 提示「{pattern_key} 复现证据：{证据}」→ **建议再重构**（该重就重，须用户确认），并附**粗略影响面**（结合第 2 步核对时的 Grep/Read 概数：受影响文件数/模块/调用处，标注「概查非穷举」防过度自信）
   - **新根因 / 新模式** → 完整重估（对抗质疑三问）+ 用户确认
5. **回写 patterns.json**：更新 `hit_count` + `last_assessment`（+ `refactor_ticket_id` 若本次确认重构）；**任一结论都提炼 `workaround` 记入**（保留最近一次）：已解决→已落地解法（第 4 步提炼）、复发→本轮修复方案、新根因→新方案——三态都产生可执行知识，杜绝「resolved 最高频却永远暂无历史方案」的空转；无方案可提炼（如纯新增功能、无规避/修复概念）则省略字段，命中者照旧显示「暂无历史方案」

**非阻塞声明**：本检查全流程**软提示，不中断、不等待用户输入**——「建议再重构」与既有 L2 警告分级一致（不在 SKILL「强制阻断边界矩阵」硬门禁内），记入思考块/产物即可，**用户确认与否流程照常推进**，不因本机制暂停分析。
