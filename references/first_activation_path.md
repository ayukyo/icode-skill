# 首次激活路径（First-Activation Path）一致性检查

> 共享机制文档（v2.14 新增）：供 [01_plan.md](../steps/01_plan.md) §5c 断言⑤ / [05_deepcheck.md](../steps/05_deepcheck.md) 阶段1 Reverse / [06_audit.md](../steps/06_audit.md) 部署后验证建议 / [08_patch.md](../steps/08_patch.md) 部署后验证发现分支 引用。**定义在本文档，各步骤只做精简内联 + 回指**，避免同一概念碎片化散落在多处。

## 定义

**首次激活路径** = 一条"写了但从没实机执行过"的历史代码路径。常见来源：重构遗留的遗留分支、被前置守卫提前拦截的兜底路径、从未被成功调用的接口。

**为什么是静态分析的盲区**：核对类检查（代码 vs 计划）发现不了这类路径上的既有 bug——因为计划往往也是基于这条有 bug 的代码设计的，**代码与计划一致、但两者都基于错误的假设**。bug 只有在首次实机激活时才暴露。

**典型病灶**：跨层/跨进程接口**两侧**（请求方 vs 接收方）对**同一字段的校验要求互相矛盾**。请求方校验接受值 X，接收方校验只接受 Y，两侧从未在实机对齐过——单独读任一侧都"看起来对"，对不齐才暴露。

## 触发条件

当 plan / 修改涉及的代码路径**从未被实机执行过**时，触发本检查。

## 检测方法（软信号，不阻断）

1. 对修改涉及的每个**跨层接口 / 请求 action**，grep 历史运行日志，确认是否有**成功调用记录**。
2. 若无成功记录 → 判定为「首次激活路径」。
3. **软信号语义（关键）**：历史日志可能不全（未留痕、被清理、跨仓库缺失），命中「无记录」**只触发「详细核对 + 输出部署后验证建议」**，**绝不阻断流程**。严禁把「无成功记录」当作硬性失败。

## 双侧校验一致性核对清单

对每个判定为「首次激活路径」的接口：

1. **Read 请求方侧**：入参校验 / 请求构造逻辑（如客户端的校验方法、请求构造方法），确认该字段接受的值域。
2. **Read 接收方侧**：对端校验逻辑（如服务端的信封校验 / 请求校验），确认该字段接受的值域。
3. **逐字段对比**两侧对同一字段的接受值要求是否一致。
4. 不一致 → 标 `[未验证-双侧校验矛盾]`，**计划必须同时修两侧**（优先「数据入口适配器」一次归一化，避免两侧各自为政的散补丁）。

## 部署后验证建议（下游输出）

凡判定为「首次激活路径」，audit 阶段应输出部署后验证建议：
> 「本工单涉及首次激活路径，部署后请跑日志验证确认该接口被成功接受。」
