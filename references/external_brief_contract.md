# 对外简报表达契约（统一真源）

> **定位**：本文件是 icode 所有「对外简报」**共用的对外表达规则唯一真源**——
> `steps/log.md` 的 `log_problem_brief.md` / `<单号>_log_problem_brief.md`、`steps/07_readme.md` 的 `_brief.md`
> 都只保留各自的输入来源 / 产物命名 / 生成时机 / 阶段差异，对外如何组织与表述一律按本契约执行。
>
> **读者**：产品 / 测试 / 其它模块研发 / 相关方——不熟 icode、不熟本模块。
>
> **核心矛盾**：根因分析与证据完整性已足够，缺的是「对外如何组织与表述」——先讲实现细节、
> 归因只有有/无、角色混淆、日志语义混淆、分析态与交付态混用、固定章节强于语义槽位。本契约逐一解决。

## 0. 三条硬规则（所有对外简报强制）

1. **开头必须是「结论与问题定位」卡**（2~4 短段），不是技术摘要；技术符号下沉到「故障如何发生」和「关键证据」。
2. **归因措辞按证据等级分级**，禁止 "这是 X 侧 Bug" 作为默认开头。
3. **修复与验证状态必须显式标注**，禁止用任何内部状态字段值推导"已修复/已验证"。

## 1. 开头「结论与问题定位」卡（必填四项）

开头用标题「结论与问题定位」，2~4 个短段依次覆盖：

1. **现象与影响**：用户/测试看到什么，业务上造成什么影响（影响谁/多严重）。
2. **主要定位**：现有证据主要指向哪条功能链或实现，标注证据等级（见 §2）。
3. **角色澄清**（需要时）：谁是实现主体 / 运行载体 / 下游表现（见 §3）；只写本简报需要澄清的角色，无歧义不写。
4. **状态边界**：结论置信度、尚未确认项、修复是否已部署和验证（见 §6）。

**禁止**：开头直接堆叠函数名 / 锁名 / 文件行号 / 算法复杂度。这些内容下沉到「故障如何发生」与「关键证据」。

## 2. 归因措辞按证据等级分级

| 证据状态 | 推荐措辞 | 禁止措辞 |
| --- | --- | --- |
| 已由代码 / 现场时序 / 修复验证闭环 | "问题定位在 X 的 Y 链路" | 情绪化或绝对化归责 |
| 主链高置信，但子阶段占比或现场版本未完全确认 | "现有证据主要指向 X 的 Y 链路" / "问题主要发生在……" | "这是 X 侧 Bug" / "唯一根因是……" |
| 只有相关性或单一日志线索 | "当前首要怀疑……" / "需通过 A/B 或插桩确认……" | "已确认" / "就是" / "必然由……" |
| 已排除某模块自身故障 | "当前未发现 X 自身异常证据" | "与 X 完全无关"（除非有完备闭环） |

**默认开头禁止 "这是 X 侧 Bug"**。即使最终责任明确，也应写成"问题定位在 X 的某条处理链路"，并说明其与宿主 / 调用方 / 下游模块的关系。

## 3. 四角色拆分（防宿主/下游误判为责任主体）

当一个算法/库运行在其它进程内，或故障通过下游模块表现出来时，按证据识别以下角色：

| 角色 | 要回答的问题 |
| --- | --- |
| 实现主体 | 缺陷逻辑实际在哪个组件或功能链 |
| 运行载体 | 哪个进程加载并执行该实现 |
| 下游表现 | 哪个模块接收到异常输出并表现出症状 |
| 观测载体 | 日志 / trace / 录制数据落在哪里 |

**硬规则**：日志出现在某进程，只能证明该进程是观测或运行载体，**不能单独证明它是责任主体**。角色归属必须以代码链路证据为准，不得从日志落点 / 进程名 / 模块名直接推导。

## 4. 「日志/观测说明」条件章节（先区分、再因果）

仅在以下任一条件命中时生成「日志/观测说明」：

- 用户或工单明确质疑"日志为什么在 X 目录/进程"；
- 同一问题中同时存在文本日志、结构化 trace、数据 dump、录包或 recorder；
- 日志记录 / flush / dump / 压缩或 I/O 本身进入故障链；
- 日志落点容易造成模块归属误判。

章节按「先区分，再说明因果」顺序写：

1. **普通文本日志在哪里、为什么在那里**：由进程 logger、库内运行方式或启动拓扑解释；明确它是观测线索还是故障原因。
2. **调试数据录制做了什么**：是否抓取快照、压缩、写盘、flush、持锁、同步等待。
3. **哪一部分进入故障链**：明确是文本打印、录制逻辑、锁等待、磁盘 I/O，还是尚不能拆分的组合。
4. **如何改**：既包含性能修复，也包含日志和可观测性改进。

**禁止**把 `logger`、`recorder`、`dump` 和"磁盘写日志"笼统写成同一件事。

**未命中条件的简单场景不生成此章节**（不机械凑满标题）。

## 5. 原因链：先业务语言、再技术锚点

「故障如何发生」使用 4~7 个编号步骤，每一步包含：

`触发事件 → 内部动作 → 延迟/错误如何传递 → 下游如何表现`

- 复杂链路可补一张小型 Mermaid 图；简单问题使用编号步骤或对照表即可。
- 技术符号首次出现时补一句中文解释（如"局部栅格地图：机器人周边用于避障的地图"、"调试数据录制器：用于离线分析的录制工具，不是普通文本打印"）。
- 源码 `file:line` 和原始日志行号放在「关键证据」，正文只保留理解因果所需的少量符号。

## 6. 修复建议三段闭环 + 状态显式

**修复建议**至少拆成：

1. **临时止血 / 根因确认**：可逆动作、影响范围、观察指标；明确这不是永久修复。
2. **永久修复**：按责任组件写治本改动；同时说明不应破坏的原有保护。
3. **验证与可观测性**：验证场景、量化阈值、必须新增的耗时或状态日志。

**修复/验证状态**（对外表达）显式标注，不得用内部状态字段推导：

| 状态 | 对外表达 |
| --- | --- |
| 仅完成根因分析 | "已完成问题定位，修复方案待实施" |
| 已有代码提交但未进现场包 | "已有候选修改，尚未在本设备/本场景验证" |
| 已部署但验证未完成 | "已部署，验证进行中" |
| A/B 或回归通过 | "已验证"，并附场景、版本和指标 |
| 因条件阻塞 | "验证因 X 尚未完成" |

`/icode log` 简报**默认分析态**（除非输入中已有可核验的部署与回归证据）；`/icode readme` 简报以 `delivery_verdict` 为交付状态来源，但仍须写清具体验证范围。

## 7. 推荐结构（语义槽位，非机械凑满标题）

**适用**：本节结构适用于 **log 简报（问题定位型）**；**readme 简报（本次变更型）按 `steps/07_readme.md`「跨领域说明模板」组织**，但归因分级（§2）/角色拆分（§3）/日志语义（§4）/修复与验证状态（§6）/首屏质量门（§8）表达规则同样适用。

开头四项为必填，其余按问题复杂度和触发条件展开：

```markdown
# {单号 + 具体症状}：问题简报   ← 单号仅 TB 源时有；本地日志简报标题只写具体症状

## 结论与问题定位          ← 必填（§1 四项）
{现象与影响}
{主要定位 + 证据等级}
{实现主体/运行载体/下游表现的必要澄清}
{修复和验证状态}

## 日志/观测说明            ← 条件触发（§4）
{普通文本日志为什么在这里，它是不是原因}
{调试数据录制/trace/dump 做了什么}
{真正进入故障链的部分，以及仍未拆分的边界}

## 故障如何发生            ← 复杂问题
1. {触发}
2. {内部动作}
3. {延迟或错误传播}
4. {下游表现}

## 关键证据
- {故障前后的量化反差}
- {触发点时序}
- {关键代码位置}
- {排除项和反证}

## 应该怎么修改            ← §6 三段
### 临时止血与根因确认
### 永久修复
### 日志与可观测性改进

## 验证标准
{场景 + 指标 + 阈值 + 版本/部署要求}

## 尚未确认的事项
{未拆分因果、缺失证据、下一步确认方法}

## 修复前后对照            ← 复杂问题或已有目标链路时（log 简报 §7.5 触发时必含）
{修复前事实 → 修复后目标；未部署必须明确标注}
```

## 8. 首屏质量门（生成后单独检查「结论与问题定位」）

- 不依赖后文即可理解现象和影响；
- 不从日志目录直接推导责任；
- 不使用超过证据等级的归因措辞；
- 不把候选提交写成现场已修复；
- 若存在宿主/下游误判风险，已在首屏澄清；
- 首屏不堆叠超过 3 个源码符号或文件位置。

## 9. 应用差异（两入口）

- `steps/log.md`：分析态默认未部署；产物命名 `log_problem_brief.md` / `<单号>_log_problem_brief.md`；需额外剔除 icode 分析流程术语（见 log.md「术语剔除清单」）；`log_analysis.md §7.5` 触发时简报「修复前后对照」必含。
- `steps/07_readme.md`：以 `delivery_verdict` 为交付状态来源；保留本次变更的接口变化 / 核心代码 / 兼容性（跨模块接口变更时必须贴必要代码，纯问题简报可只列关键证据）；面向"本次变更"统领，不区分功能/查BUG。
