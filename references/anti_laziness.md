# 反偷懒约束（共享规则）

> 本文件是 icode 所有步骤共享的「反偷懒约束」。SKILL.md 不再重复本段，各 step 执行前**必须 Read 本文件完整内容**（同会话已读不豁免，Read 后输出 `📖 已 Read references/anti_laziness.md` 确认行）。

## 硬性总则

**禁止以"省 token / 省时间 / 简化产出 / 已大致足够"为由偷工减料**。任何步骤的产出必须**完整**完成本步骤定义的所有子项、维度、轮次和文件，**不得合并、不得跳过、不得降级**。

## 典型偷懒行为（一经发现，该步骤产出视为不合规）

1. **合并产出**：把多个独立步骤的产物揉进同一个文件（如把审查和定稿合到一个文件、把代码和复检合并写）
2. **跳过子项 / 省略产物文件**：步骤定义里要求的子项/维度/章节漏写或写"略"、"同上"、"参考前文"；**步骤明确要求的 `.json` / `.md` / `.log` 等产物文件缺失或内容是空模板**（漏写文件=漏子项，合并到本条）
3. **降低轮次**：步骤 2 审查、步骤 5 复检要求的轮次未达标就提前终止（如 `max_rounds=3` 只跑 1 轮就声称"已无新问题"）
4. **示意/伪代码替代实现**：步骤 4 编码时用 `// TODO`、`// ...`、`// 省略类似实现` 等占位符代替真实代码
5. **审查/复检走过场**：审查意见全是"无问题"、"通过"等空泛结论，无具体证据
6. **跳过分级思考（reasoning gate）**：L2/L3 步骤未调 sequential-thinking 或降级文字思考块、L1 步骤未记 `.decision_anchors.json` 决策字段、未写 `.thinking_gate_trace.jsonl`（详见 [mcp_per_step.md](mcp_per_step.md)「通用前置·分级思考」+ [thinking_core.md](../references/thinking_core.md) + [thinking_detail.md](../references/thinking_detail.md)）
7. **跳过自检报告**：修改后未输出完整的 7 维自检报告
8. **跳过对抗验证**：步骤 2.5 逐维审查产出的 issue 未经独立质疑者子代理对抗就下 `confirmed` 结论（**步骤 2.4 已用 Read/Grep 实证验证失败的 issue 例外**，已有铁证可直接 `confirmed` 无需对抗）；或把主代理推理过程喂给质疑者当既定事实（破坏独立性）；或对抗未收敛时和稀泥默认通过（详见 [adversarial.md](adversarial.md)）。**质疑者必须用 Agent 工具独立 spawn，不得主代理自演**——产物（review_round_*.json 的 adversarial_verification）必须记录每个质疑者的**独立 Agent 调用证据**（spawn 的 agent 返回内容摘要），无 spawn 证据=自演=不合规。**子代理失败时禁用自演兜底**：质疑者返回空/截断/无 verdict 时，按 adversarial.md「子代理失败处理」重试 2 次（含 1 次换 subagent_type）→仍失败诚实降级为 `[未验证-子代理对抗失败]` 计入 `pending_verification`，**绝不改由主代理自演裁决、绝不伪造 confirmed**（自演=既当运动员又当裁判，确认偏误倾向确认自己结论，对抗形同虚设）。主代理 Read/Grep 实证铁证属事实核查不算自演，判断性结论才必须独立 spawn
9. **伪造共识 / 默认通过**：issue 无 `evidence_pointer` 证据回指就确认；断言无法实证验证时不标 `[未验证-证据不足]` 而默认通过；对抗裁决分裂时不降级而强行 `confirmed`
10. **跳过历史检索 / 污染产物**：`/icode init`/`/icode plan`/`/icode start`/`/icode log` 未执行历史检索注入（全局索引存在时）；或把历史参考内容写进 `00_init.md`/堆砌进 `01_plan.md`（污染工程产物）；或命中工单后照抄历史决策而不顾当前需求差异（检索规则见 SKILL.md「历史检索复用」段）。**`00_init.md` 全文（含对话摘要段）不得出现任何历史工单引用**（如"参考 demo-1 ADR-1"），历史参考只进会话上下文
11. **跳过偏差回写 / 污染计划**：步骤6 终审未把实质偏差汇总回写到 `03_plan_final.md` 的「实现偏差备忘」段（含无偏差时未写"无实质偏差"留痕）；或回写时改了计划正文（破坏对照价值）；或把细节差异堆砌进备忘（抬高回读噪音）；或步骤4 主动偏离计划未记入 `code_deviations`（偏差回写规范见 [06_audit.md](../steps/06_audit.md)）
12. **注释/日志/风格/优雅偷工**：步骤4 编码漏写导出函数/关键分支/数据结构注释；关键路径（错误返回/状态跳转/外部交互/决策分支/降级重试）漏加日志导致运行时无法排查；步骤5 复检/步骤6 终审未把注释完备性+日志覆盖纳入检查（漏检即放行）；或引入项目未使用的新日志库。**风格/优雅偷工**：新增代码不复用既有工具函数（重造轮子）、命名/错误处理/日志/注释格式与同模块既有代码不一致、调用链模式与工程既有模式冲突（如工程用注册模式新代码写 switch-case）、**跨模块/跨端点调用绕过工程既有主导模式**（如工程统一走路由/事件分发却用直调，或路由/接收器已注册却不用、同函数内既有同类调用走某模式新增却另选他法）、顺手重构无关既有代码、过度暴露 public 符号（YAGNI 违反）——这些"功能对但风格突兀"的代码视为偷工，步骤5 须检查优雅度6条（①复用优先 ②风格对齐 ③调用链模式一致 ④最小侵入 ⑤接口克制 ⑥调用路径选择（架构一致性）——新增跨模块调用必须 grep 既有同类调用对齐主导模式，编译通过≠模式正确），不达标记 issue。**命名红线（硬性，O-3）**：标识符禁止含设计清单/工单编号样式前缀（如 `b5_`、`MC#`、`p3` 等编号样式临时前缀）、禁止含与语义无关的工作流临时前缀——命名只准表达工程语义（如 `refresh_due`、`fail_backoff_ms`）；审查时 grep 全仓确认新命名有先例/同构，**全仓零先例的唯一命名 = 命名污染信号**。**魔法值红线（硬性，O-3）**：非 `0/1/true/false` 且**含业务语义**的裸数字字面量（退避时长/超时/轮询间隔/阈值等）不得直接内联在函数体逻辑中，必须提升为**命名常量**（类成员 `uint32_t xxx_ms_{1000};` 或 `static constexpr`）并置于配置区；审查时 grep 函数体无含语义裸数字字面量。**边界**：switch 分支值/数组索引/边界比较等无语义负担的字面量不强制提升（防过度设计）。**注释工程化（不写 icode 工作流元数据）**：步骤4 编码时不得在代码注释里写 icode 内部元数据（ticket_id / 步骤号 / 审查轮次引用 / 内部文件名引用 / 流程术语如"按 icode 步骤落地"）——这些信息归 git commit / CHANGELOG / 内部工单系统。**注释只写工程语义**（功能/参数/边界/不变量/为什么这么设计），未来读者不应需要懂 icode 才能看懂代码
13. **日志根因分析偷工**：`/icode log` 跳过基线检查直接 grep 日志；对抗分析质疑者未独立 spawn 或未独立读日志（主代理自演）；伪造根因共识（证据不足不降级）；根因结论无日志行回指；或照抄历史工单根因不顾当前症状差异；或盲信 TB 评论/他人文档中的根因结论或修复手段（未实证即采信，把别人观点当事实——评论只作参考启发，须日志原文实证 + 代码事实验证门核对，见 [steps/log.md](../steps/log.md) 阶段2「TB 评论研读」+ 阶段3「上游假说继承/接力模式」）（详见 [adversarial.md](adversarial.md)）。**必须独立 spawn 3 个质疑者子代理（证据质疑者/替代解释者/充分性质疑者各一），每轮独立调用 Agent 工具分别 spawn，不得合并 spawn（3 in 1 视为主代理自演）；spawn 规格：`subagent_type: "general-purpose"` + schema 强制结构化输出，禁用 Explore（实测 Explore 在长指令下只调研不裁决、被截断在调研阶段）**；log_analysis.md/adversarial_verification 必须记录每个质疑者的**独立 spawn Agent ID**（如 `agentId: ac32afbc15a278f3f`），无 Agent ID 记录=未 spawn=偷懒=不合规。**子代理失败时按 adversarial.md「子代理失败处理」重试 2 次（含 1 次换 subagent_type）→仍失败诚实降级 `[未验证-子代理对抗失败]`，禁用主代理自演兜底**。**代码事实验证门**：根因假设涉及代码行/函数时，必须先 Read 实际代码验证再报告，不得仅凭日志推断代码行为。**设计意图证据采集门（防"把有意设计误判为缺陷"，与代码事实验证门并列）**：对可疑/反直觉/违反历史工单门禁/默认值魔法值的代码行，**判"缺陷"前必须先做 git 演进史设计意图采集**（git blame → commit message → 关联文档回归日志 → 测试注释 → 输出"缺陷/有意设计/待对抗确认"判定，见 [steps/log.md](../steps/log.md) 阶段1「设计意图证据采集」），不得把"缓存初值/哨兵值/兼容行为"直接当缺陷；历史工单结论与当前代码冲突时**必须按证据权威优先级裁定**（当前 HEAD 代码 + git 演进史 > 历史工单结论，见 [steps/log.md](../steps/log.md) 阶段1「证据权威优先级」），不得以旧结论为基准去"证伪"最新代码（方向颠倒会产出回归既有修复的错误方案）
14. **references 软引用未实读**：step 文件写"见 references/xxx.md"但执行时**未用 Read 工具实读该共享文件**，凭 SKILL.md 概述或记忆执行——新会话里 references 内容不在上下文，凭记忆执行必出错。**引用 references 的步骤，必须先 Read 该文件完整内容再执行**，否则该步骤产出视为不合规。**同会话已读不豁免**：每步仍须重新 Read（显式Read是深度思考的前置仪式，凭记忆会降级思考质量），Read 后输出确认行 `📖 已 Read references/xxx.md` 作为合规证据
15. **思考块过薄**：强制思考降级文字块每子项只有一句话带过（如"与步骤1一致""通过"），未展开实质推演。**每个思考子项必须有 ≥2 句实质内容**（具体设计点/具体检查项/具体风险），步骤2独立方案构思须≥3设计点、步骤5每阶段须列具体检查项、步骤6追溯矩阵须逐功能点定位代码。**步骤5 Free 阶段每个角度必须 ≥3 个具体检查点（文件名+行号）**，仅1句简述=过薄=不合规；**02_review.md 不得只有摘要**，必须含每轮审查的维度结果+对抗验证记录（可引用 review_round_*.json 但须有实质要点摘录，不得仅写"见json"）；**步骤5/6 每阶段开始必须输出 `📖 已 Read` 确认行列出实际 Read 的代码文件**（基于前步记忆写=偷懒=不合规）；**步骤5 Free 每角度强制表格 ≥3 检查点（file:line）、Fixed 每维度 file:line 证据**；**步骤6 不得复用步骤5结论**（"步骤5无新问题→步骤6也无新问题"=偷懒），必须独立列"步骤5未覆盖/更深层角度"逐个查 + 6维度每维度 file:line 证据；**步骤5/6 末尾必须填自检清单**（未填项标 ❌=不合规）；**步骤2.5.5 对抗每个质疑者必须记录独立 spawn Agent ID**（无 Agent ID=自演=不合规）
16. **stale 检测执行写类 Git 操作**：历史检索/过时校验/主动 stale 扫描中执行了 `git checkout`/`switch`/`reset`/`stash`/`clean`/`commit`/`add`/`rm`/`rebase`/`merge`/`cherry-pick`/`push`/`fetch`/`pull`/`branch -D`/`tag -d` 等任一写操作或网络操作（白名单仅 `rev-parse`/`merge-base --is-ancestor`/`status --porcelain`/`log --oneline`（含 `--since`/`-- <路径>` 只读变体）/`cat-file -e` 等只读命令）。stale 检测**只读工作树现状，绝不改工作树/索引/提交**；"checkout 变化重评"=检测用户外部改了 HEAD 后只读重评，**绝不由技能主动 checkout**（详见 [dir_and_metadata.md](dir_and_metadata.md)「过时校验·Git 操作安全白名单」）
17. **待决策倾向自审走过场**：步骤0 思考阶段「待决策倾向自审」子项未逐条回溯现状盘点/影响面分析证据，只写"已自审、倾向不变""无需修正"等空泛结论无反证依据；或只做确认式自审（"证据支持倾向 B"）而不主动找反证（"有没有证据反对 B"）；或回指停在节级（"回指第2节"）不到证据点--确认偏误导致倾向照单全收。**必须**：①每条倾向都问"有无反证"；②回指到第2/4节**具体证据点**（file:line 或具体接口/模块名），不得仅写"回指第2节"；③无反证显式记"已查无反证"+证据点、有反证就地修正倾向并记反证依据、若某倾向确无代码证据（纯设计/产品偏好）显式记"无代码证据-留步骤1 ADR"不得编造证据点；④**本子项不适用第16条"每子项≥2句"最低标准**，须逐条倾向各记反证搜索+证据回指；⑤倾向证据须为步骤4 Read/Grep 实证结果，段零注入的 project_docs/module_docs 快照不得作为倾向证据（详见段零文档不盲信约束）。`00_init.md` 第5节须持久化每条倾向的审计结果（已查无反证+证据点 / 已修正+反证 / 无代码证据-留步骤1 ADR），思考块记推演过程。**与第9条边界**：第9条针对步骤2.5 issue 真伪的**终局裁决**（须独立 spawn）；本条针对步骤0**草稿步**初步倾向校准（步骤1 ADR 将独立正式决策），虽含判断但因属草稿非终局，主代理自审即可，不触发对抗 spawn
18. **链路图偷工**：`00_init.md`（init 直出第 6 节 / log 转出第 4 节）链路图是「最终改什么」的一图流总览。偷工表现：整节缺失或仅写"待补"；before/after 不画具体 ASCII 链路（无节点+箭头+file:line/模块锚点）；改动点清单与第 3 节新增需求点矛盾或遗漏；after 图改动点无法回指 file:line/模块；多轮讨论后链路图未随正文同步更新（图与正文脱节：init 版对齐第 2/3/4 节即现状·需求点·影响面、log 版对齐第 1/2/3 节即症状·根因·需求点）。**必须**：每轮涉及 before 依据（init 现状 / log 带 bug 链路）、after 依据（init 改动方案 / log 修复方案）或第 3 节需求点任一变化时同步刷新链路图；before/after 为具体 ASCII 链路，信息不足画已知部分 + `?` 标未定节点；图上 `[+]`/`[~]`/`[-]` 标注与改动点清单一一对应、改动点「关联需求点」回指第 3 节（一个需求点可对应多个改动点）；log 转出版 before 取自 `log_analysis.md` 阶段 1 状态链路图
19. **跨分支 prev 误判增量**：`/icode doc` 步骤 3 工程增量判定 / `dir_and_metadata.md` 段零 stale 检测，均依赖 `git diff <prev_commit>..HEAD --name-only` 判定增量范围。偷工表现：未先 `git merge-base --is-ancestor <prev> HEAD` 校验祖先关系就直接用 `git diff`，导致**分支切换 / fork / 换库**等场景下 `git diff` 因 merge-base 远而**完全失真**（可能 diff 出大部分文件当变更、或漏判关键变更），模型仍误把"几乎全章变更"当"普通增量"处理。**必须**：①`git diff <prev>..HEAD --name-only` 之前**强制先跑** `git merge-base --is-ancestor <prev> HEAD`（白名单内只读命令）；②退出 0（prev 是 HEAD 祖先）→ 可信，按 diff 命中做增量；③退出 1（HEAD 是 prev 祖先/分叉 / 不同分支）→ **`git diff` 不可信，必须按"新工程/另一版"全量重生成/全章判定 stale**，不再走增量判定（文档步骤：按"新模块独立分析"处理，stale 检测：直接标 stale 不看 diff）；④退出 128（prev 不可达如 GC/换库）→ 同上全量处理。**禁止**：仅看 diff 行数大、命中章节多就当作"正常大增量"继续——必须先排除祖先合法性这一前提，否则一切 diff 判定都是噪音（实测踩坑：用户切分支重写后，跑 doc 步骤把"几乎全工程变更"误判为大批量增量）
20. **跨分支借鉴 project_docs / module_docs 不核对分支**：DOC 步骤生成的工程文档 `project_docs/<project_id>/<branch>/_meta.json`（**按分支分目录存储**，如 `project_docs/myproject/main/_meta.json` vs `project_docs/myproject/feature/_meta.json`，切分支跑 doc 自动落到对应分支目录、天然隔离不互相覆盖）+ 模块文档 `module_docs/<key>/_meta.json` 均**显式持久化分支字段**（`branch`/`head_commit` 或模块 `branch`/`current_commit`）。下游 init/plan/log/start/fast 段零注入此文档作思考输入时：①**段零只读当前分支子目录**（不交叉读 `<project_id>/` 下其他分支目录，避免跨分支复用——分支子目录隔离有第二层防误借鉴作用）；②但仍须比对当前 cwd `git rev-parse --abbrev-ref HEAD` + `git rev-parse --short HEAD` 与当前分支目录下 `_meta.json.branch` + `head_commit` 兜底：分支不一致（如 `_meta.json.branch = main` 但当前在 `feature`，或 stale 文件漂移导致子目录错位）→ **整个 project_docs 当 stale 处理**（按「stale 章节降级注入」只注简要说明 + ⚠️ 警告行，**绝不注正文**），因为"在 main 看到的"≠"在 feature 看到的"——接口/调用链/契约可能差很多，盲目照搬带歪下游 init/plan；③**模块文档分支与工程 pin 分支不一致**（如模块文档基于 `dev` 但工程 `.gitmodules` / `.repo/manifest.xml` pin 在 `main`）→ 同上，整个 module_docs 当 stale 降级注入；④**detached HEAD 视为特殊态**（`_meta.json.branch = null` 或分支目录落 `(detached)`）→ 跳过分支校验，只走 commit 一致性 + 锚点校验 + 不盲信约束。**禁止**：①仅看 commit 短哈希貌似一致（detached HEAD 切到任意 commit 都可能"碰巧"等于一个旧 commit）就当新鲜文档注入——**必须 branch 优先**，branch 不一致直接降级不注入正文；②**禁止**段零检索时跨分支混读（如当前在 `feature` 时把 `main` 子目录下章节也纳入候选集），即使 top-N 排序看似更相关——分支隔离是硬约束不是软推荐（实测踩坑：用户切到 feature 分支跑新需求，模型把 main 分支上的 module_docs 当新鲜参考注入，导致 ADR/接口完全跑偏）

**代码检索统一走文本层**：符号/引用/调用点定位统一用 grep/Read/git grep（ripgrep 未装时用 grep，本机默认即 grep）。定位定义 `grep -n '^<sig>'` / `grep -rn '<name>('`，找调用点 `grep -rn '<name>('`，跨仓库/子仓库用 `git -C <子仓> grep` + `grep -r`（多 git 根 0 命中误判见下方「跨仓库/子仓库检索」段）。**代码事实验证门**（log 阶段3 / plan / code / review / deepcheck）由 Read 实读 + grep 检索完成：Read 是全文层、grep 是检索层，两者互补；根因假设涉及代码行/函数时，必须 Read 实际代码逐行核对再进对抗/编码，不得仅凭日志/文档推断代码行为。代码检索用 grep/Read 属于步骤常规动作，无需额外留痕。

37. **日志有版本证据仍直接用当前 HEAD 解释现场（治"现场代码未绑定、用后来的代码解释更早的现场"）**：`/icode log` 必须在 grep 日志前执行「现场运行版本基线门」（见 [steps/log.md](../steps/log.md) 阶段1「现场运行版本基线门」）——日志或版本文件含明确 Git 版本标识（启动日志打印的 git hash/commit/revision/sha、`build_info.json`/`version.json`/固件 manifest/包版本清单、二进制 `--version` 输出等）时，**不得默认当前 HEAD 就是产生日志的那一版**。**偷工表现（7 类，任一命中即违规）**：①日志/版本文件有版本标识却跳过提取，直接用当前源码解释现场行为；②无版本证据时把当前 HEAD 自动填成"现场版本"（应标 `unknown` + 显式降级"现场运行版本未确定"）；③把 operation UUID/请求 ID/文件校验和误识别为 Git Hash（未校验"出现在版本语义附近 + 能唯一解析为 commit"两条件）；④多仓库工程只记 super repo HEAD、不按模块分别绑定（子仓/独立业务仓库漏绑）；⑤Hash 本地不可达时自动 fetch 或静默跳过（应如实记录降级，由用户决定是否补齐仓库对象）；⑥根因代码事实不注明"取自现场 Hash 还是当前 HEAD"（现场行为结论默认引用当前 HEAD）；⑦判定矩阵未执行——现场 Hash 有缺陷但当前 HEAD 已修复时仍重复设计同一修复（应定位修复提交、建议同步/验证，不重复写修复）。**必须**：①按版本证据来源优先级收集现场版本（启动日志打印 > 版本文件/manifest > 二进制输出 > TB 评论[须再验证] > 无证据标 unknown）；②Hash 识别须同时满足"版本语义附近 + 正确仓库唯一解析为 commit"（短 Hash 冲突记歧义不猜测）；③按模块版本矩阵分别记录（现场 Hash / 当前 HEAD / 二者关系 / 证据来源），多仓库不互相替代；④历史源码一律只读 Git 命令读取（白名单见 [references/dir_and_metadata.md](../references/dir_and_metadata.md)「Git 操作安全白名单」），禁止 checkout/switch/reset/stash/clean，分析阶段不自动 fetch；⑤根因代码事实注明取自现场 Hash 或当前 HEAD；⑥现场与当前行为不同时按判定矩阵给结论（仍需修复 / 已修复→定位提交建议同步 / 后续回归→不能反向解释更早现场 / 无法确定→降置信度）；⑦带 `dirty` 标记的 Hash 只能定位基础提交，置信度不得标高。**落盘**：三基线（现场运行/当前分析/修复验证）写入 metadata `runtime_code_baselines`/`analysis_code_baselines`/`verification_code_baselines`（缺省 `[]` 向后兼容，见 [steps/log.md](../steps/log.md) 步骤9 + [references/dir_and_metadata.md](../references/dir_and_metadata.md)「metadata 三基线字段」）。**与第 13/34/35 条边界**：第 13 条治 log 根因分析整体偷工（基线/对抗/回指），第 34 条治 §7.5 修复前后对照，第 35 条治对外简报表达，本第 37 条专治**「现场运行版本未绑定、用当前 HEAD 解释现场」的版本基线偷工**——先绑定现场版本再用它解释现场日志，与既有"当前 HEAD 判断现在是否仍需修复"互补不替代。
38. **替用户选择业务策略（治"证据证明了机制缺口，却把业务策略当机制结论直接定"）**：workflow gate 语义决策门禁（见 [SKILL.md「工作流硬门禁」](../SKILL.md) + [mcp/workflow-gate/gates.json](../mcp/workflow-gate/gates.json)）——当分析/计划/评审出现**同一输入有两种及以上会改变外部行为的处理方式**、结论含"待确认/未定义/需要选择/策略不唯一"、需决定允许·拒绝·合并·替换·保留·迁移、需决定存活身份·冲突优先级·兼容阈值·失败语义、或当前证据只能说明缺机制不能唯一推导期望行为时，**AI 不得自行以"最保守/最安全/通常如此"选定策略**。**偷工表现**：①把"策略未定义/存在多选项"的机制证据直接换成"建议采用 X 方案"当作已定结论进入实现；②在 log/plan 阶段替用户拍了板（选存活身份/冲突优先级/失败语义）却未写入 `semantic_decisions` 且未获 `user_confirmed`；③diagnosis-only 未标记就带着未解决决策进入 plan/code/patch。**必须**：①把策略选择写入 `semantic_decisions`（`{dimension, alternatives, selected, evidence, user_confirmed, status}`），用户明确选择才 `status=resolved, user_confirmed=true`；②未确认前 plan/code/patch 不得继续（`python3 tools/lint_workflow_contract.py --step code` 阻断）；③本轮只做诊断 → 标 `diagnosis_only=true`（"仅诊断"，允许结束但不进实现）。**与第 1/9/16 条边界**：第 1 条治合并产出、第 9 条治伪造共识（默认通过）、第 16 条治待决策倾向自审走过场；本第 38 条专治**"证据证明机制缺口后，把业务策略选择当机制结论由 AI 直接定"**——证据可以证明机制缺口，但不能代替用户选择业务策略。
39. **单场景通过即部署（治"只验证直接功能结果，漏异步/重启/重放一致性就标记完成"）**：workflow gate 生命周期验收门（见 [SKILL.md「工作流硬门禁」](../SKILL.md) + [mcp/workflow-gate/gates.json](../mcp/workflow-gate/gates.json)）——对**改变权威状态或实体身份**的修改，只验证"权威提交后直接查询通过"**不能**把任务标记 `delivery_verdict=verified`。**偷工表现**：①只测直接查询/直接功能结果，跳过异步收敛、重启恢复、重复执行（重放）一致性；②`impact_contract.identity_change=true` 但 9 维影响清单没填完整（漏依赖引用/运行时索引/聚合选择器/恢复路径）就进部署；③验收矩阵 `phases × consumers` 有空 cell 仍标 verified；④单场景验证通过后过早部署，后续逐个部署逐个发现链路缺口。**必须**：①plan 阶段对改变权威状态/身份的变化生成 `acceptance_contract.matrix`（覆盖 `immediate`/`converged`/`restart`/`replay` × `direct_query`/`aggregate_selector`/`persistent_reference`/`external_projection` 全部必填单元）；②deepcheck 逐项逆推复检（即时/异步/重启/重放一致，无法本机验证的标 `[未验证-需真实环境]` 不得写成通过）；③audit 终审前跑 `lint_workflow_contract.py --step audit-verified`，矩阵不完整 → `delivery_verdict` 不得 `verified`（只能 `verification_pending`/`blocked`/`not_applicable`）；④部署前冻结完整场景矩阵，真实环境验证同一批覆盖所有高风险场景，新失败先归类（缺失需求/遗漏影响消费者/实现缺陷/环境观察偏差——前两类回计划或评审，不在代码阶段追加修补）。**与第 3/5/9 条边界**：第 3 条治降低审查轮次、第 5 条治审查走过场、第 9 条治伪造共识；本第 39 条专治**"验证偏重直接功能结果、把单场景通过当成完整验收"**——即时状态、异步收敛、重启恢复、重复执行的一致性缺一不可。

## 为什么强制

本工作流的价值在于"完整闭环 + 多轮审查 + 充分思考"，任何偷懒都会破坏闭环、放过隐藏缺陷、最终把质量负担转嫁给后续维护。**省下的 token 远小于因质量下降而需返工的代价**。

## 用户授权例外

仅当用户**明确显式**说"跳过步骤 X" / "只跑 1 轮"等指令时才可降级，且必须在产出文件中明确记录"已按用户指令降级，跳过的内容包括：..."。模型不得自行降级、不得擅自合并。
