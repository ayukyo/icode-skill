# DOCX 内容组织与图示

适用于按真实材料编写、重写技术 Word 文档。仅忠实转换 Markdown 时不加载，不把这里的写作建议变成擅自改写原文的授权。

## 章节围绕主题

先确定每份文档要回答的问题，再安排章节，不把仓库目录或函数清单直接变成目录。开头说明本文对象及核心原理，然后沿主流程解释 SDK、系统或设备怎样协作。需要的接口和边界放在对应环节；默认不另堆源码索引，用户明确需要时再提供。

| 主题 | 正文应说清 | 合适的主要图示 |
|---|---|---|
| 框架 | 分层职责、公共对象与内部组件、扩展点、依赖和生命周期 | 分层图、对象关系图；详细协议另属流程文档 |
| 数据流程 | 数据从哪里产生、经过谁、格式如何变化、何时交给应用；队列/线程只解释必要影响 | 一帧数据路线、处理前后格式、必要的异步交接 |
| 命令流程 | 参数/属性/接口对应关系、设置前提与顺序、一条命令完整收发、错误返回 | 参数映射表、设置顺序图、具体命令收发时序 |
| 升级流程 | 升级对象、入口、文件类型、写入与状态变化、应用下一步、失败处理 | 不同升级方式对照、一条完整升级时序、状态与应用动作 |
| 对时/同步 | 哪个时钟或时间戳改变、基准从哪里来、脉冲作用、时间值经过哪些模块、单位 | 接线图、SDK调用链、时间值转换图；不可混为一张图 |
| 计算/算法引擎 | 输入、处理位置、输出、坐标/公式/单位、调用方式与限制 | 处理链、空间坐标、带数值的计算例子 |

这是选题参考，不是每份文档都必须套用的固定目录。章节数量以能连贯讲清主题为准；一节只有一句重复结论时合并。多份文档共享背景只写一次，其它位置用简短关联说明。不要加“谁应该看哪份文档”的读者分工，除非用户要求。

## 文字让人能通读

- 先说动作和对象，再给正式名称：“电脑上的应用调用 SDK，把基准时间发给相机”，比只列模块名更容易理解。首次出现缩写，紧接中文职责；之后用稳定名称，不反复换同义词。
- 一个段落解释一个问题。保留必要的因果、条件和结果，不用删除中间环节来追求短。不要用“闭环、对齐、链路、赋能、承载、落点”等抽象词代替具体动作。
- 表格只用于对应关系或比较。步骤顺序集中写一次，不把顺序拆在表格、图注和后面的小节中。参数说明至少给出可调内容、类/属性/接口、适用条件和顺序；不贴大量代码。
- 流程图旁只补图不能表达的条件。图已经完整表达顺序时，正文不逐箭头重述；公式或时间转换要补一个自洽的小例子。
- 保留理解原理所需的坐标轴、原点、方向、单位、输入/输出定义。修改后检查 X/Y/Z 是否齐全、符号是否前后一致、数值能否代入。

## 以当前实现为依据

先解析用户指定源码根及当前基线，不用旧知识库代替当前代码，也不在正文写入本地开发环境的目录称呼。按“公开接口 → 实际实现 → 下游处理 → 返回/回调”核对完整路径，追到真正的操作或计算处；不要把代理调用误写成执行位置。

重点检查：默认值、参数类型、权限/机型支持、执行条件、异步线程、单位换算、成功和失败、重试/再次调用的条件、回调状态以及应用接下来要做什么。同一个状态出现两次，说明两次的调用位置与阶段，不能只复用一行状态名称。

正文在相关段落给必要的**相对路径和关键接口**，例如“入口见 `include/.../Device.hpp` 的 `updateFirmware()`；真正执行见 `src/...`”，路径和接口必须来自实际源码。框架总览不需要塞满源码细节；不强制给正文所有句子附行号。审计目录保留更精确的依据：

```json
{
  "files": [
    {
      "path": "src/example.cpp",
      "sha256": "已审读文件的64位SHA-256",
      "anchors": [{"start": 20, "end": 38, "contains": "实际代码片段"}]
    }
  ]
}
```

用 `tools/docx/verify_sources.py record.json --root <源码根>` 检查文件与行范围；hash 和片段一致只是来源检查通过。解释是否准确仍需读实现及调用方。源码变动时重新核对，不能只刷新 hash。

看不到固件或闭源实现时，区分“SDK代码确认的动作”和“通用原理说明”。示意图中的推测必须明确标为原理示意/待确认，不画成已读到的内部调用。源码检查也不能当成实机精度、接线或硬件功能验证。

## 图示先讲含义，再选工具

每张图只回答一个主要问题。绘图前确定主体、输入/输出、读图方向、要说明的动作、事实来源和必要图注。图内名称与正文、代码对象一致，正文提到的关键对象在图里应能找到。

| 图类型 | 必需表达 | 容易误导的省略 |
|---|---|---|
| 分层/对象关系 | 层边界、模块职责、公共句柄与内部实例的关系；注明箭头是调用、依赖还是持有 | 把不同对象都画成同一模块，或没有图例 |
| 流程图 | 开始/结束、真实步骤、判断条件、各分支结果 | 删除边上的条件，把带条件分支画成必经步骤 |
| 时序图 | 应用、SDK模块、传输层、设备/固件等实际参与者；从上到下完整收发，返回与回调明确区分 | 只有调用没有应答；把SDK和固件画在同一运行位置 |
| 接线图 | 电脑/开发板、设备、外部信号源及实际连线；电信号和软件控制区别 | 没有依据的“外部时源直接调用应用”箭头 |
| 时间转换 | 每个时间值属于谁、谁换算/写入/调整、前后单位、基准或偏移来源 | 只写“对时”，没有说明改的是时钟还是帧时间戳 |
| 坐标图 | 原点、X/Y/Z轴正方向、空间量含义与单位；透视计算给输入参数 | 用距离代替Z、丢一根轴、把未按比例示意当测量图 |

复杂图按问题拆开，不把全部模块和所有细节硬塞进一张。长时序按实际阶段拆图，保留连续编号和阶段间返回关系；重复的等待、失败或再次调用注明条件，不能为了紧凑改写代码行为。

### 模块配色与图例

已有文档优先复用其**模块名称 → 颜色 → 含义**，其它章节及局部修改不得另造模块或配色。新文档集合在第一次绘图时确定一份共享 palette，图源/脚本复用它；不是每张图临时选色。

不同模块用易分辨的色相，文字/边框与底色保持足够对比；同模块不同层级可用边框、分组或深浅区分，不改变模块身份。不要只靠颜色表达语义，结合名称、位置、图例和线型。不存在的模块不要为了凑图例添加；物理连线、调用、返回/回调等箭头的含义应明确且一致。

### 能力选择

- 架构、流程、时间轴、坐标等技术图优先保留 SVG 图源；照片和截图用 PNG/JPEG，正文、公式和数据表保留可编辑对象。SVG 只接受 `diagram_svg.py` 的静态受限子集，中文字体通过 `--svg-font` 或 `ICODE_SVG_FONT_FILES` 明确选择并校验字形。
- Markdown 相对 SVG 默认按物理尺寸和 DPI 转为 PNG，报告 `raster_fallback`。保留 SVG、PNG 和 manifest，不手工更换缓存或只刷新 hash。`--svg-mode dual` 同时嵌入 SVG 与 PNG，报告 `native_vector_pending`；实际 Office 打开、缩放、PDF 导出、再保存与逐页检查完成前不得宣称原生矢量验收通过。

- 普通文字、表格、本地图片：`build_docx.py`。
- 简单线性图：内置 Mermaid 渲染。它只支持明确的小子集，不是完整 Mermaid 引擎。
- 常见收发时序：`draw_sequence.py` 用本地JSON生成带参与者、步骤编号、请求/应答、自调用和条件文字的PNG；必须传共享 palette，不替用户另选模块颜色。适合2～5个参与者、最多10步的单阶段图，更长或含循环/并行的过程分阶段或使用专用脚本。
- 分支、带标签/条件的复杂流程、时序、坐标：优先复用已有图源和脚本；否则用宿主可用的图示/文档能力，或自管 Python + Pillow 的本地绘图脚本制作图片，再嵌入 DOCX。可用的能力按需加载，不强制依赖特定插件。
- Word样式、复杂表格、局部替换：用自管 `python-docx` 或可用文档能力，保留源文快照和构建脚本。不为修一张图重新生成整个文件。

技术图优先采用可重复生成、能精确控制标签的方式。自动生成的图和截图都要核对文字、箭头、比例、颜色及原理。fallback 代码只保留图源，不算完成图示。

收发时序图的最小图源（名称和步骤应换成实际代码确认的内容）：

```json
{
  "title": "一次设置请求的收发",
  "participants": [
    {"id": "app", "label": "应用程序", "role": "application"},
    {"id": "sdk", "label": "SDK", "role": "sdk"}
  ],
  "steps": [
    {"from": "app", "to": "sdk", "text": "调用设置接口"},
    {"from": "sdk", "to": "sdk", "text": "检查参数"},
    {"from": "sdk", "to": "app", "text": "返回结果", "reply": true}
  ]
}
```

palette 是模块名到 `fill/stroke/text` 的JSON，每项用 `#RRGGBB`，从现有图例取色。执行 `draw_sequence.py sequence.json sequence.png --palette palette.json --manifest sequence.manifest.json`，保留两个输入及图像hash，再作为本地图片嵌入Word。实线为调用/请求，虚线为返回/应答；其它信号或回调要在图源文字/图注中明确，不能只凭线型猜测。

## 内容与最终页面检查

交付前逐项回答：文档是否紧扣主题；第一次读能否找到原理和完整流程；关键术语是否解释；步骤、状态、接口和单位是否与代码相符；图和正文对象是否一一对应；有无重复；有无为了简化删掉必要条件、坐标或说明。核对每张图的关键箭头和分支，不能仅检查图片数量。

随后对**最终保存的 DOCX**执行结构检查、受管渲染，查看每一页：图中字大小、箭头和文字是否遮挡，颜色是否可分辨，长表格是否跨页难读，图注和图是否分离，标题是否孤立，页眉页脚是否正常。有问题修正后重新检查受影响内容和全部最终页面。

在 manifest 的 `content_review` 记录核对范围、依据和未验证项；在 `visual_qa.page_review` 记录实际看过的页面及结果。`render_docx.py` 会先设为 `pending`；渲染成功不是人工阅读通过，自述的“passed”也不是源码语义的机器证明。
